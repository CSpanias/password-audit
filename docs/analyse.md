# Analyse

The `analyse` command evaluates recovered NTLM and optional LM password
datasets, summarises common weaknesses, and generates reports. It does not run
Hashcat; use [`crack`](crack.md) to recover passwords first, or
[`audit`](audit.md) to orchestrate the full workflow.

## Usage

The mapped NTLM dataset is required. Supporting files default to the
`ntds-organiser/` directory:

```bash
password-audit analyse \
    --mapped-ntlm-passwords ntds-organiser/mapped-ntlm-passwords.txt \
    --mapped-lm-passwords ntds-organiser/mapped-lm-passwords.txt
```

The LM dataset is optional. Analysis can use the enabled-user list, Domain
Administrator list, domain policy, company-word list, and LM-user list
generated by [`organise`](organise.md).

| Option | Purpose |
| --- | --- |
| `-M`, `--mapped-ntlm-passwords` | Required mapped NTLM dataset. |
| `-L`, `--mapped-lm-passwords` | Optional mapped LM dataset. |
| `-D`, `--domain-admins` | Domain Administrator account list. |
| `-P`, `--pass-policy` | Domain password policy. |
| `-G`, `--company-words` | Organisation-related password terms. |
| `-E`, `--enabled-users` | Enabled account list used for summary statistics. |
| `-U`, `--lm-users` | Accounts associated with LM hashes. |
| `-O`, `--output` | Report output path; the selected format extension replaces its extension. |

Use `password-audit analyse --help` for all aliases and default paths.

## What is analysed

The report summarises recovered-password counts, unique passwords, recovery
rate, and LM exposure. Findings cover:

- Recovered Domain Administrator passwords.
- LM hash storage and Domain Administrator LM exposure.
- Passwords below the configured minimum length.
- Password reuse, including reuse among similarly named accounts.
- Common, username-derived, organisation-related, date-based, and keyboard
  pattern passwords.

Finding IDs, severity, category, descriptions, and remediation guidance are
defined in the packaged YAML files. Severity is attached to individual
findings; the report does not calculate an overall risk score.

## Report formats

Without `--format`, analysis writes Markdown and HTML. Supported formats are
`markdown`, `html`, `json`, `yaml`, and `sarif`; an explicit selection writes
only those report formats.

```bash
# Default Markdown and HTML reports
password-audit analyse \
    --mapped-ntlm-passwords ntds-organiser/mapped-ntlm-passwords.txt

# Select formats and an output base name
password-audit analyse \
    --mapped-ntlm-passwords ntds-organiser/mapped-ntlm-passwords.txt \
    --format json sarif \
    --output audit-report
```

For the default output path, the reports are
`password-audit-report.md` and `password-audit-report.html`. With
`--output audit-report --format json sarif`, the report files are
`audit-report.json` and `audit-report.sarif`. The findings sidecar
`password-audit-findings.json` is written in every case.

The HTML report is self-contained and works offline. Its narrative sections
include **Copy Markdown** buttons. The remediation section also contains
References under a level-three heading; the references are included when that
section is copied.

JSON, YAML, and SARIF contain the structured report data. The separate
findings sidecar has this shape:

```json
{
  "findings": [
    {
      "id": "PWD-AUDIT-001",
      "title": "Password Audit",
      "description": "A total of 79 plaintext passwords were recovered from 273 enabled accounts.",
      "severity": "info",
      "category": "general",
      "remediation": "Review the findings in this report and prioritise remediation based on severity. Address critical and high findings first to reduce the risk of credential-based attacks.",
      "evidence": [],
      "affected_assets": [],
      "references": []
    }
  ]
}
```

Finding records support evidence and affected-asset fields, but the current
analysis does not populate them with account-level evidence.
