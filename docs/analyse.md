# Analyse

The `analyse` command evaluates recovered NTLM and optional LM password
datasets, summarises common weaknesses, and generates reports. It does not run
Hashcat; use [`crack`](crack.md) to recover passwords first, or
[`audit`](audit.md) to orchestrate the full workflow.

## Usage

The mapped NTLM dataset is required and supporting files default to the
`password-audit/` directory; the LM dataset is optional:

```bash
password-audit analyse \
    --mapped-ntlm-passwords password-audit/mapped-ntlm-passwords.txt \
    --mapped-lm-passwords password-audit/mapped-lm-passwords.txt
```

Analysis can use the enabled-user list, Domain Administrator (DA) list, 
privileged group membership, domain policy, company-word lists, and LM-user 
list generated by [`organise`](organise.md).

Privileged membership is loaded automatically from
`password-audit/privileged-users.json` when present. For another output
directory, pass `--privileged-users` with the path to the generated file.
If it is unavailable or incomplete, the report and console say so.

Hash reuse is analysed from the organiser's `password-audit/ntds-users-clean.txt`
when present and the mapped passwords are also in `password-audit/`. For other
locations, pass `--ntds-users` with the corresponding organised file's path.
The file contains enabled NTDS users after filtering, including hashes for
passwords that were not recovered. If it is unavailable, the report says so.

A curated `./company-words.txt` file is also included automatically when 
present; use `-G` to select a different curated list. Curated terms supplement 
generated terms.

| Option | Purpose |
| --- | --- |
| `-M`, `--mapped-ntlm-passwords` | Required mapped NTLM dataset. |
| `-L`, `--mapped-lm-passwords` | Optional mapped LM dataset. |
| `-D`, `--domain-admins` | Domain Administrator account list. |
| `--privileged-users` | Organiser-generated privileged group membership JSON. |
| `--ntds-users` | Organiser-generated enabled NTDS user records for hash reuse analysis. |
| `-P`, `--pass-policy` | Domain password policy. |
| `-G`, `--company-words` | Optional curated terms added to generated terms; `./company-words.txt` is auto-detected when present. |
| `-E`, `--enabled-users` | Enabled account list used for summary statistics. |
| `-U`, `--lm-users` | Accounts associated with LM hashes. |
| `-O`, `--output` | HTML report output path. |

Use `password-audit analyse --help` for all aliases and default paths.

## What is analysed

The report summarises recovered-password counts, unique passwords, recovery
rate, and LM exposure. Findings cover:

- Recovered DA passwords.
- Recovered NTLM passwords for members of selected privileged groups.
- LM hash storage and DA LM exposure.
- Passwords below the configured minimum length.
- Password reuse, including reuse among similarly named accounts.
- Matching NTLM hashes across enabled user accounts, including passwords not
  recovered; affected accounts in selected privileged groups are highlighted.
- Common, username-derived, organisation-related, date-based, and keyboard
  pattern passwords.

Finding IDs, severity, category, descriptions, and remediation guidance are
defined in the packaged YAML files. Severity is attached to individual
findings; the report does not calculate an overall risk score.

See [Checks](checks/index.md) for what each analysis looks for, how it works,
and how to interpret the results.

The selected groups are DAs, Enterprise Admins, Schema Admins,
Administrators, DNSAdmins, Account Operators, Backup Operators, Server
Operators, Cert Publishers, and Exchange Windows Permissions.

Group membership does not represent every privileged account or attack path, 
and the impact of membership depends on the environment. The broader finding 
includes DAs as well as the separate DA finding; an account in multiple groups 
is counted once and its groups are listed together. The existing DA LM analysis 
remains separate.

The hash-based reuse finding and recovered-password reuse findings may overlap;
their counts should not be added together. Technical commentary includes sample
account groups and masked hashes; the finding lists all affected account groups
without full hashes or plaintext passwords. Examples involving selected
privileged accounts show each account's groups alongside the other accounts.
Account and group labels in report tables omit domain qualifiers
for readability; full identifiers remain in the organiser exports and the
hash-reuse finding. Accounts not identified in selected
privileged groups are not necessarily unprivileged, particularly when membership
coverage is incomplete.

## Reports

Analysis writes a self-contained HTML report and, by default, a JSON findings
sidecar.

```bash
password-audit analyse \
    --mapped-ntlm-passwords password-audit/mapped-ntlm-passwords.txt

password-audit analyse \
    --mapped-ntlm-passwords password-audit/mapped-ntlm-passwords.txt \
    --output audit-report.html
```

The default report is `password-audit-report.html`; `--output` can set a
different name. Its extension is always `.html`. By default, findings are written to
`password-audit-findings.json` in the current working directory.

The HTML report is self-contained and works offline. Each narrative section's
**Copy Markdown** button copies its content without the section title. 
**Copy All Markdown** copies all available narrative sections with their
titles. Remediation references are included as Markdown links under a
level-three References heading in both copy options. In the HTML report,
each reference is a clickable link.

The default JSON findings sidecar has this shape:

```json
{
  "findings": [
    {
      "id": "PWD-AUDIT-001",
      "title": "Password Audit",
      "description": "A total of 79 plaintext passwords were recovered from 273 enabled accounts.",
      "severity": "info",
      "category": "general",
      "remediation": "Review the findings in this report and prioritise remediation based on severity. Address critical and high findings first to reduce the risk of credential-based attacks.",
      "evidence": [],
      "affected_assets": [],
      "references": []
    }
  ]
}
```

The hash reuse finding includes affected account groups in its evidence and
affected accounts in its affected-assets field. Other findings do not
currently populate these fields with account-level evidence.
