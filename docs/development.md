# Development

This page describes the repository layout, the main workflow boundaries, and
the commands used to validate changes.

## Set up a development environment

Install the package and documentation dependencies in an editable environment:

```bash
git clone https://github.com/CSpanias/password-audit
cd password-audit
uv venv
uv pip install -e ".[docs]"
```

The project requires Python 3.10 or later. Hashcat is only needed to run
password-recovery campaigns.

## Repository layout

| Path | Responsibility |
| --- | --- |
| `cli/` | Argument parsing and command dispatch. |
| `auditing/` | End-to-end workflow and input validation. |
| `ntds/` | NTDS/BloodHound parsing, dataset analysis, mapping, and exports. |
| `cracking/` | Hashcat integration, campaign validation, execution, estimates, and statistics. |
| `lm/` | LM recovery-result mapping. |
| `analysis/` | Password analysis and narrative report content. |
| `analysis/finding_defs/` | YAML definitions for finding titles, severity, categories, and remediation. |
| `reports/` | Markdown, JSON, YAML, SARIF, and HTML renderers. |
| `tests/` | Python `unittest` tests. |
| `docs/` | MkDocs documentation source. |

`site/` is generated by MkDocs, ignored by Git, and uploaded as a Pages
artifact by the documentation workflow. Edit the Markdown files under `docs/`
instead of editing generated files.

## Architecture

User-facing commands keep argument parsing separate from reusable workflows:

```text
cli command
    ↓
workflow orchestration
    ↓
parsing and analysis
    ↓
datasets, campaign results, or rendered reports
```

The `audit` workflow coordinates `ntds`, `cracking`, `lm`, and `analysis`.
Standalone commands expose parts of the same workflow for users who need to
prepare data, run campaigns, or analyse an existing dataset separately.

The analysis workflow builds a shared report payload. The renderers in
`reports/` consume that payload to produce the requested format; the
`password-audit-findings.json` sidecar is also written for compatibility.

## Validate changes

Run the test suite and, when Ruff is installed, lint the Python files:

```bash
python -m unittest discover -s tests
ruff check .
```

Ruff is a development tool and is not installed as an application dependency.

Build and preview the documentation:

```bash
uv run mkdocs build --strict
uv run mkdocs serve
```

The GitHub Pages workflow installs the `docs` optional dependency and builds
the site from the repository root.

## Contribution checklist

- Keep CLI modules thin and put reusable behavior in workflows or domain
  modules.
- Add focused tests for behavior changes.
- Update the relevant guide when command options, outputs, or workflows change.
- Run the tests, lint, and strict MkDocs build before submitting a change.
